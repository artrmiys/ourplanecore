## 1. Где мы были на 2026-07-03

OurPlaneCore перерос статус «клона PlanSwift» и местами обгоняет оригинал. Это полноценный продукт: ~90 команд в палитре, 8 рабочих вкладок, трёхпанельная оболочка.

**Фичи, которых нет у PlanSwift из коробки:**
- Офлайн Count Similar с поиском повёрнутых/зеркальных символов (bit-packed matcher).
- AI Fill (авто-переименование + авто-масштаб листов) с **самообучающимися правилами**.
- 3D-крыша со стропилами (ридж/хип/валли по уклонам).
- Извлечение материалов/спецификаций из исходных PDF.
- Report Builder под личные Excel-шаблоны (TemplateCom.xlsm), экспорт в открытый Excel через COM.

**Технические сильные стороны (редкость даже в коммерческих аналогах):**
- **Исторически отмеченные защиты хранения:** атомарная запись (temp + `File.Replace`), обработка повреждённого JSON, 20 metadata-снапшотов на джобу, восстановление после краша с lock-файлами, корзина `.undo`. Это не гарантия отсутствия потерь: область каждого reader, lease, операции и восстановления проверяется отдельно; snapshots не заменяют полный внешний backup.
- **Обработка ошибок:** глобальные хендлеры (`DispatcherUnhandledException`, `AppDomain`, `TaskScheduler`), которые перед показом ошибки сбрасывают автосейв на диск.
- **Логи:** TSV в `%AppData%\OurPlaneCore\logs\`, ротация по 10 МБ, чистка за 90 дней, потокобезопасно, не роняет апп.
- **404 регрессионных теста** на алгоритмическом ядре (геометрия, matcher, экспорт, roof math, PlanSwift import).
- **Производительность:** 5 слоёв кэшей рендера, вынесенный Python-воркер (PyMuPDF), дебаунс автосейва 500 мс, in-memory кэш Data.xml.

**Главные архитектурные риски:**
1. **God-class `MainWindow`** — один класс на 149 partial-файлов, ~46k строк, общее изменяемое состояние. Сдерживается дисциплиной именования файлов, но рассуждать об инвариантах тяжело.
2. **Мёртвый код 3D massing** — ~15 файлов `MainWindow.Massing*`, полный AI-планировщик и roof recognition написаны, но заглушены `Legacy3DMassingWorkflowEnabled => false`. Живая замена — вкладка «3D».
3. **Нет версионирования** у core-форматов (`measurements.json` — голый массив, `Data.xml`) — миграции держатся на толерантной десериализации. _(Частично закрыто, см. §2.)_
4. **Историческая оценка июля: Redo отсутствовал**, undo был фрагментирован. Не переносить это утверждение на текущий код: clipboard Undo/Redo и его main/detached поведение имеют отдельную реализацию и проверки. Общая архитектура истории действий остаётся предметом дальнейшего аудита.

## 3. Исторический бэклог июля (статус уточнён на 2026-09-06)

Отсортировано по отношению польза/риск.

1. **Cancel + прогресс у AI-запросов.** Утверждение июльского аудита «все вызовы с `CancellationToken.None`» больше не соответствует коду: `MainWindow.AiRequestActions.cs` создаёт CTS и передаёт token, потеря write access отменяет работу. В `BusyOverlay` пока нет обычной кнопки Cancel и счётчика «N из M»; этот UI и terminal-state проверки остаются в текущем плане.
2. **Машинные AI-ответы → строгий json_schema.** `RunStructuredJsonAsync` используется legacy massing-планировщиком; live actions/metadata всё ещё извлекают fenced JSON через `CandidateJsonBlocks`. Typed schema нужна для машинных действий, с явной обработкой refusal/incomplete/validation failure и сохранением human review. Свободные текстовые заметки не требуют перевода; улучшение требует тестов, а не даёт надёжность автоматически.
3. **Промпты в UI.** Таксономия суффиксов, allowlist масштабов, форматы JSON зашиты строками в `OpenAiRequestRunner`. Прямой кандидат на паттерн «8 Settings» (навык `add-editable-rule`).
4. **Замкнуть writer версии measurements.json.** Когда reader из §2 раскатан на всех машинах — переключить `SaveMeasurements` на запись конверта со `schema_version` и добавить точку миграции в `ParseMeasurementDtos`.
5. **Count Similar AI: дать apply-путь или оставить как есть.** Сейчас ответ только висит в Inbox. Либо позволить скорректировать счёт по ответу, либо оставить чисто справочным (подпись уже честная).

**Осознанно НЕ делаем сейчас:**
- Большой MVVM-рефакторинг `MainWindow` — заморозит развитие на месяцы, а дисциплина partial-файлов риск сдерживает. Стратегия из CLAUDE.md верна: новая логика только в `Models/`, куски выносить по мере того, как их всё равно трогаешь.
- Удаление мёртвого 3D massing — соблазнительно (чистит вес), но код рабочий и пригодится для нового 3D. Он уже в git-истории и `docs/archive/`. Удалять только когда новый 3D-пайплайн стабилизируется.

## 4. Стратегические направления

Главный вопрос: чем OurPlaneCore отличается от PlanSwift / Bluebeam. Ответ уже виден в коде — **замкнутый цикл обучения**. Цикл авто-переименования/масштаба — единственное место, где фидбек реально меняет поведение (правила с support ≥ 3, видны и переключаемы в Settings), и он **работает**. Это доказательство концепции. Второй цикл (marker feedback) пишется на диск, но фактически никуда не идёт.

### Направление A — AI-такеофф (основная ставка) ⭐

Весь конвейер уже собран: crop → запрос → драфт геометрии → ревью-диалог → реальные `Measurement`. `Find Similar From Marker` делает это end-to-end.

**Следующий шаг:** масштабировать с «одного маркера» до «пройди лист и задрафти все стены/проёмы» — с обязательным ревью перед применением. И **замкнуть marker-feedback цикл** так же, как замкнут sheet-metadata цикл: сейчас он только инжектит последние ~12–24 записи в промпт, без агрегации и генерации правил. Довести до правил с порогом, как в `SmartLearningStore.Rules`.

_Почему это ставка:_ никто в нише не делает локальный обучающийся AI-такеофф, который учится на **твоих же правках**. Это единственное реально защищаемое преимущество.

### Направление B — глубина estimating

Окно Estimating и Report Builder под xlsm уже есть. Логичное развитие — **база сборок (assemblies)**: «стена = стойки + обвязка + OSB» из погонного метра, чтобы такеофф сразу превращался в смету. Именно за это в PlanSwift берут деньги как за плагины.

### Направление C — готовность к раздаче воркерам

Судя по рабочему процессу (проверка такеоффов воркеров), прога может стать командным инструментом. Тогда приоритеты: онбординг (sample job уже есть — хорошо), **redo**, защита от кривых рук, и фичи ревью — сравнение двух версий такеоффа, отметки «проверено».

### Рекомендация

**A — приоритет.** Он строится на уже существующем конвейере, не требует нового ядра, и это то самое, что делает продукт не-заменяемым на PlanSwift. B и C — сильные, но вторичны: B монетизируется, C нужен когда команда растёт. Порядок: **A → (redo из §3/C) → B**.

**В одну строку:** техническая база крепче, чем у большинства коммерческих аналогов; процессные дыры дёшевы в починке (часть уже закрыта); стратегическое преимущество — самообучающийся AI-такеофф, и семя этого уже растёт в коде — его и поливать.
